## 3. 원본 해석 계약 — 오프셋과 번호

### CHK 섹션

`scenario.chk.gz`를 gunzip한 뒤 4바이트 태그 + LE uint32 길이 + payload 순서로 끝까지 읽는다. 범위 초과/누락/잘못된 필수 길이는 오류로 중단한다. 현 원본에 같은 섹션 중복은 없다. 필요한 섹션: PUNI(5700), UNIx(4168), STR , TRIG(328×2400), FORC(20), OWNR(12). build의 기존 SCX/CHK 해시 확인은 반드시 유지한다.

### PUNI — 단순히 첫 228바이트를 읽으면 틀린다

단위 u=0..227, 플레이어 p=0..11 (모두 0기반):

```js
const override = puni[p * 228 + u];           // 12×228
const defaultAvailable = puni[2736 + u];     // 228
const useDefault = puni[2964 + p * 228 + u];  // 12×228
const available = useDefault !== 0 ? defaultAvailable !== 0 : override !== 0;
```

이 원본은 인간 플레이어가 P1/P2/P3와 P5/P6/P7이다. OWNR 값=6, FORC의 앞 8바이트는 `[0,0,0,1,2,2,2,3]`이다. 미니스타 사령관 ID와 원본 슬롯의 대응은 **`{0:0,1:1,2:2,3:4,4:5,5:6}`**으로 고정한다. `team * 3 + slot`을 원본 플레이어 인덱스로 그대로 쓰지 않는다. 현재 50종은 인간 슬롯별 차이가 없지만 판정 함수는 override를 지원해야 한다.

PUNI가 허용이라고 해서 해당 ID를 새 건설 상품으로 추가하지 않는다. **현재 지원 건물 50종 ∩ 해당 사령관의 PUNI 허용**이 카탈로그다. 영웅·자원·목표물·비건설 개체는 추가하지 않는다. ID 130(감염된 커맨드 센터)도 인간 슬롯에서 금지지만 현재 건설 그래프 밖이므로 별도 상품 추가/삭제 작업은 없다.

### UNIx·STR

- u의 기본값 사용 플래그: byte[u]. 현재 50종은 전부 0(사용자 지정)이다. 향후 1로 바뀌면 조용히 저장 필드를 비용으로 쓰지 말고 이번 지원 범위에서는 빌드를 실패시킨다.
- 미네랄 uint16 LE: `2280 + 2*u`; 가스: `2736 + 2*u`; 이름 STR ID uint16 LE: `3192 + 2*u`.
- STR의 첫 uint16=개수, 이어지는 uint16 오프셋 배열, 문자열은 NULL 종료다. ID는 1기반이고 ID0은 빈 이름이다. 범위와 NULL 종료를 확인한다. cp1252로 해석하고 표시용 이름에서는 제어 문자 U+0000..U+001F를 제거한다.
- 원본 별칭은 `originalName` 근거 필드로 보존한다. 게임의 한국어 건물 이름/아이콘/유닛 이름을 이 별칭으로 전역 덮어쓰지 않는다. 카드에는 '코버트 옵스'와 '시즈 탱크 3기'가 함께 보여야 한다.

### TRIG

- 모든 문서·새 테스트·새 데이터의 `triggerId`는 **1기반 물리 레코드 번호**로 통일한다. 기존 `desert-strike-evidence.json.triggers` 키는 0기반이므로 접근 시 `triggerId-1`이다.
- 레코드 2400바이트. 조건 16×20바이트(0..319). 조건 unit uint16=+12, 비교=+14, type=+15, flags=+17. type3=Bring, 비교0=AtLeast, 비교1=AtMost.
- 액션 64×32바이트(320..2367). unit uint16=액션+24, type=+26, count=+27, flags=+28. type11=CreateUnitWithProperties. **uint32 +20은 propertyIndex**다.
- disabled 비트는 조건/액션 flags `& 2`이다. 다른 비트(예:16)를 disabled로 오인하지 않는다. 레코드 소유자는 +2372..2399.
- 생산 루프는 **#219..#276**만 대상으로 한다. 다른 트리거의 Create(전초기지·벙커·특수기 등)를 정규 출격 편성으로 섞지 않는다.
- Force1 소유 레코드(owners=[18]) → 미니스타 team0, Force3(owners=[20]) → team1. #219..247은 team1, #248..276은 team0다. 물리 레코드의 앞뒤 순서를 team0/1로 오인하지 않는다.
- `building-catalog-source-audit.json.productionTriggers`에는 이 58개 레코드의 소유자·Bring·생산 유닛·수량·속성 번호·바이트 해시가 있다. 비용/종류/수량을 이 값과 대조한다. 이름 텍스트를 파싱해 수량을 결정하지 않는다.

## 5. 저글링 보너스의 정확한 수정

**[6,8]로 복원한다. 대칭화하지 않는다.** 원본 Force1(#275/#276)은 남은 풀 6개 이상일 때 6기, Force3(#246/#247)은 남은 풀 8개 이상일 때 6기다. 나머지는 5기다. README의 #245/#274는 벌처 트리거이므로 수정한다.

한 사령관의 한 웨이브에서 완성·생존·비행 아님 조건을 통과한 풀을 기존 producer 순서로 처리한다. 남은 풀 수 n을 먼저 정한 뒤 각 풀을 처리하고 하나씩 감소시킨다. 다른 사령관의 풀을 합치지 않는다. 개별 건물 조회에서도 전체 풀의 순서를 먼저 계산하고 조회 필터는 그 뒤 적용한다(`activeWave`의 기존 순서 유지).

총 저글링 = `5*n + Math.max(0, n - threshold + 1)`.

| 완성된 풀 n | team0, T=6 | team1, T=8 |
|---:|---:|---:|
| 0 | 0 | 0 |
| 5 | 25 | 25 |
| 6 | 31 | 30 |
| 7 | 37 | 35 |
| 8 | 43 | 41 |
| 9 | 49 | 47 |

미완성/비행/죽은 풀은 n에서 제외한다. team0에서 6풀 중 하나 미완성이면 25기다. team1에서 8풀 중 하나 미완성이면 35기다. 첫 풀의 개별 조회는 각각 6기이고 마지막 풀은 5기다. 카드의 정적 설명은 '저글링 5~6기'로, 실제 출격 현황은 계산된 수량으로 표시한다. 건물 생성 순서를 바꿔 총합이 바뀌면 안 된다.

## 6. 파일별 구현 설계

### A. 원본 추출과 생성 데이터

1. **신규 `tools/desert-strike-source.mjs`**: 순수 함수로 `readChkSections(chk)` 및 `deriveBuildingCatalog(chk, rules)`를 export한다. 외부 패키지·브라우저·전투 모듈 import 없이 Buffer와 원본 bytes만 사용한다.
2. `deriveBuildingCatalog`의 후보는 `Object.keys(rules.costs)` 50종이다. 반환 형태는 아래로 고정한다. player 배열은 12칸 boolean, 키는 숫자 ID를 문자열화한다. 별도의 가격/편성을 카탈로그에 중복 저장하지 않는다.

```js
{
  buildingCatalog: {
    '117': { originalName: '3 Siege Tanks', sourceNameStringId: 46,
             availableByPlayer: [/* P1..P12, exactly 12 booleans */] },
    // all 50 entries including disabled 120
  },
  poolBonusThreshold: [6, 8]
}
```

3. 추출 과정에서 UNIx의 50종 비용(가스 포함)을 `rules.costs`와 비교하고, TRIG 양 진영의 기본 편성을 `rules.waves`와 비교해 차이가 나면 빌드 오류로 중단한다. ID0 마린은 falsy 검사로 누락하지 않는다. 142는 5기 기본·6기 보너스 두 분기를 분리해 검사한다. 생산 ID 집합 자체도 정확히 비교해 누락·추가를 잡는다.
4. `tools/build.mjs`의 'One checked original-map snapshot' 블록에서 기존 해시 확인 후 이 함수를 호출한다. `rules.poolBonusThreshold`가 추출값과 다르면 실패한다. `rules.buildingCatalog=derived.buildingCatalog`를 넣어 기존 `dist/desert-strike-data.js`를 생성한다. 생성 파일만 손으로 바꾸는 수정은 금지한다.
5. `resources/desert-strike-v1.json`: `poolBonusThreshold`를 [6,8]로 수정. `source.sections`에 PUNI, STR , FORC, OWNR를 추가한다. 아래 비생산 용도 문자열을 `buildingRoles` 객체로 저장한다. 28종 생산 편성은 그대로 둔다. `buildingCatalog`는 build가 생성하므로 이 JSON에 수동 복사하지 않는다.
6. `resources/desert-strike-evidence.json`: 기존 필드를 보존하고 PUNI/STR /FORC/OWNR 원본 payload의 base64를 추가한다. 제공된 SCX/CHK는 수정하지 않는다. `original-desertstrike.json`의 source 해시도 변경하지 않는다.
7. `tools/audit-desertstrike.py`: `poolBonusThreshold=[6,6]` 하드코딩을 없애고 기존 decoded trigger의 Force 소유자와 Bring 조건으로 [6,8]을 구한다. group 설명의 'symmetric pool threshold 6'도 원본 비대칭 보존으로 바꾼다. 감사 문서 생성 테이블에 PUNI 기반 건설 허용 열을 넣고 머신샵을 금지로 표시한다. 도구 재실행으로 새 정책이 사라지지 않아야 한다. 현재 rules를 읽어 유지하는 `buildingRoles`/source.sections를 지우지 않는다. `original-desertstrike.json`의 해당 mappedRule 설명도 생성기와 맞춘다. 원본 bytes를 설명 수정에 맞춰 고치지 않는다.
8. Python 감사 도구는 지형 파일 준비가 필요하다. 재생성 시 `/tmp`에 CHK·desert.cv5·desert.vf4를 압축 해제하고 `python tools/audit-desertstrike.py /tmp/.../scenario.chk /tmp/...`를 실행한다. 그 뒤 `npm run build`를 실행한다. 기존 map.objectives 등은 build의 현재 계산을 유지한다.

준비 명령은 아래 그대로 사용한다. 최초 SCX/CHK 일치 검증은 제1절에서 이미 완료했다. 이 재생성 단계는 저장소의 검증된 CHK를 사용하므로 별도 다운로드가 필요 없다.

### B. lane 전용 허용 판정

`dist/lane-rules.js`에 아래 export를 추가한다. 카탈로그·ID·사령관이 없으면 false다. 현재 모든 인간 슬롯의 값이 같더라도 하나의 슬롯만 검사해 복제하지 않는다.

```js
export const SOURCE_PLAYER_BY_COMMANDER = Object.freeze({0:0,1:1,2:2,3:4,4:5,5:6});
export function isLaneBuildingAvailable(type, commanderId=0) {
  const sourcePlayer = SOURCE_PLAYER_BY_COMMANDER[commanderId];
  return Number.isInteger(sourcePlayer) &&
    DESERT_STRIKE.buildingCatalog?.[Number(type)]?.availableByPlayer[sourcePlayer] === true;
}
```

`dist/autobattle.js`에서만 적용한다. 공유 `tech.js`의 120 정의는 남긴다.

- `teamBuildReason(team,type,parent,morph)`에서 spec/race 확인 직후 `isLaneBuildingAvailable(type,this.ownerByTeam[team])`를 검사한다. 금지 시 정확히 `원본 맵에서 건설할 수 없는 건물입니다.`를 반환한다. 자원·선행·부착 조건보다 먼저 검사한다.
- 위 검사는 지불·부모 예약·유닛 생성·가스 점유·spendingHistory 기록 전에 실행한다. `startConstruction`이 같은 검사를 다시 거치는 구조를 유지한다.
- lane에서 `buildingOptions(worker)`를 override하고 `super.buildingOptions(worker)` 결과를 해당 건설자의 사령관 허용 여부로 filter한다. 기본 숨김 건설자의 commanderId=0이다. 다른 종족/미완성/없는 건설자는 기존처럼 빈 목록이다. 부착·변태 시설을 일반 건설 목록에 섞지 않는다.
- `addonOptions(unit)`와 새로 override할 `morphOptions(unit)`도 unit.commanderId의 허용 여부로 filter한다. 부모가 없으면 빈 배열이다. 자원/선행 부족의 허용 건물은 후보 목록에 남기고 기존 reason으로 카드를 비활성화한다.
- `build→placement→buildReason`, `addon→addonReason`, `morph→morphReason`, `AI→teamBuildReason→startConstruction` 전 경로를 막는다. 문자열 `'120'`도 거부한다. UI에서 숨기는 것만으로 끝내지 않는다.
- `placementForTeam`은 현재처럼 순수한 지형/겹침 판정으로 유지한다. 여기에 허용 판정을 섞어 AI 공간 예약을 망가뜨리지 않는다.
- `waveProducers`도 현재 owner에 대한 카탈로그 허용 여부를 검사한다. 금지된 producer를 수동으로 생성해도 출격원이 되지 않는다. 120의 wave는 만들지 않는다. `productionOptions`를 일반 BW 수동 훈련으로 되돌리지 않는다.
- 기존 부모 소유·완성·부착 점유·SATISFIES·건물/가스 한도 판정을 보존한다. 하위 사령관은 `withCommander`의 owner를 사용한다. 공통 함수에 team0=항상 인간이라는 가정을 넣지 않는다.

4. 필수 명령을 독립 실행하고 실제 브라우저에서116/비생산 문구·3종족 목록·모바일 배치를 검증한다. README 표와 실행 데이터의49허용/28생산도 기계 비교한다.
